## 1. 意图

P0 只证明「离线回归 + 确定性门禁」可用；P1 用这套门禁**驱动修复真实缺陷**，再把评测从「替身 embedding」升级到「真实 embedding/rerank 的检索级评测」，并把 Trace 数据变成可查询的监控接口。

一句话：**先把已知会答错的坑修掉，再证明真实检索质量可测量、可对比、可监控。**

## 2. 目标 / 非目标

### 2.1 目标

1. 修复 7 项已知缺陷（§3），每项有独立回归用例与门禁证据。
2. 建立 Holdout 30 题集（分层 10/5/5/5/5）与防污染流程，开发期间不可见逐题答案。
3. 跑通 `live + scope=retrieval_only` 的真实 embedding/rerank 检索评测，指标绑定 dataset/corpus/index/pipeline/gate 版本。
4. 用 P1 真实结果校准门禁阈值（gate v0.2），建立 P1 release baseline；跨版本只分析不放行。
5. 提供只读监控 API（管理员权限），能查 trace、延迟分位、成本、门禁状态。
6. 全程不改业务 API 请求参数与响应 Body 的**字段结构**（允许错误码与文案取值修正，见 §9 决策 D-3）、不改业务库/索引库 schema、不新增生产依赖。

### 2.2 非目标（P2/P3 再说）

- live 端到端（生成答案）的 40 题质量矩阵；Ragas 软指标；Langfuse 导出。
- 容量（100 资料 / 10000 记录 / 3 并发）、供应商 429/超时/5xx 系统性验证。
- OCR 真实质量评测（Holdout 不含需 OCR 的题；`requires_ocr` 仍只在 P2 live 执行）。
- Web 看板、趋势图、告警、HTTPS/域名部署。
- 供应商实账核对（账本仍是保守口径，不等于账单）。
- 不新增生产依赖；不引入 Ragas/Langfuse/OTel/Prometheus。

### 2.3 反目标

- 用放宽断言、跳过失败样本、改判分器的方式让 P1 门禁通过。
- 把 P0 的 offline baseline 直接当 P1 放行依据（embedding 变了，`pipeline_version` 必须变）。
- 为修复缺陷而顺手改 API Body 字段结构或业务库 schema。
- 开发期间读 Holdout 题目/答案来"调参"。

## 5. 真实检索级评测（live + retrieval_only）

- **范围**：只做检索（索引重建、查询 embedding、rerank、指标与门禁），**不生成答案、不调用 chat**，因此不产生 chat 费用，也不把"答案质量"混进 P1 结论。
- **索引**：用 `corpus/enterprise-20261101`（69 文件 / 155 题键），在隔离目录 `var/eval/runs/<run_id>/index/` 建索引；真实 embedding（`text-embedding-v4`，1024 维）；索引版本 `index_revision` 写入 manifest。
- **查询**：每个 case 一次 query embedding + 一次 rerank（走真实 provider），不调 chat；`path=RAG`；OCR 题标 `skipped_requires_ocr`，不入分母。
- **指标**：`Recall@10`、`MRR@10`、`nDCG@10`、`hard_filter_violation_rate`、`empty_recall_rate`；按 stratum 与总体分别报告，不设综合分；样本不足 → `unknown`（退出码 3）。
- **版本绑定**：`dataset_version` / `corpus_manifest_sha256` / `index_revision` / `pipeline_version`（真实 embedding 配置会改变它）/ `gate_version` / `mode=live` / `scope=retrieval_only`，每条 `CaseResult` 都带。
- **与 P0 的关系**：真实 embedding 改变检索结果 → `pipeline_version` 变化 → P0 release baseline **不能用于放行**，只能 `--compare-with` 做跨版本分析；P1 首次运行只能用绝对阈值，随后 `gate --calibrate` 出提案、审批后建立 P1 release baseline。
- **失败语义**：provider 错误/超时/预算拒绝 → 该 case `error`，门禁 `data/config`（退出码 3）或硬失败，不得静默跳过；零重试（沿用 controlled 执行约定）。
- **成本控制**：运行前成本预检（估算 token × 官方标价，超阶段剩余即拒绝）；pilot 先跑 10 题确认单价，再跑全量；成本写入共享账本，报告只写保守口径。

## 6. 监控 API（只读）

- 位置：`backend/src/mktkb/observability/routes.py`，挂 `/api/v1/observability/*`；权限 `Depends(require_role("admin"))`（复用现有管理员鉴权）。
- 端点（草案，实现时可微调命名，但不得少项）：
  - `GET /api/v1/observability/traces/{trace_id}`：单次执行 trace + spans（只含哈希/计数，不含原文）；
  - `GET /api/v1/observability/requests/{request_id}/traces`：同一产品请求的全部尝试（含 replayed/attempt）；
  - `GET /api/v1/observability/metrics?window=24h`：按 path/outcome 聚合的条数、P50/P95 延迟、Token、成本、degraded 次数；
  - `GET /api/v1/observability/runs/{run_id}`：最近评测 run 的 `run_manifest`/`summary` 摘要与门禁状态。
- 约束：只读（无写路径）；不返回问题原文/答案原文/上下文（只返回哈希与长度）；**不暴露 Holdout 逐题明细**（只返回聚合）；响应结构与错误码沿用现有 API 约定；新增 OpenAPI 描述并更新接口文档；新增路由仅管理员可见。
- Trace 生产默认关闭（P0 约定），本地/评测显式开启；监控 API 在 trace 关闭时返回空聚合并说明，不报错。
