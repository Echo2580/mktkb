## 4. 主要缺陷与发现

### P0-1：LLM 问答链路整体不可用，84/155 题返回服务异常

**现象**

- 所有需要语义理解/正文回答的题目（semantic、legal、ocr、rrem 以及部分 exact）返回 `service_error`。
- 错误码以 `MODEL_CALL_FAILED` / `MODEL_UNAVAILABLE` 为主。
- 账本中本轮 `chat` 预留为 **0**；服务日志中没有任何 DeepSeek `/chat/completions` 请求。
- 说明请求在本地预发送阶段被拒绝，根本没有产生供应商调用。

**最可能触发点**

`MKTKB_MODEL_MAX_INPUT_TOKENS=6144` 被用作 **UTF-8 字节闸门**，而检索证据（system + user JSON）通常超过 6144 字节：

- `rag/providers.py`：`input_bytes > chat_max_input_tokens` → `ChatUnavailable`，发生在预算预留和 HTTP 之前。
- `providers/budgeted.py` 也有相同的 `upper_bytes` 闸门。
- 该异常被上层统一包装成 `MODEL_UNAVAILABLE` / `MODEL_CALL_FAILED`，真实原因丢失（与已知缺陷 D1 一致）。

**影响**

- 语义题 0/31、法规题 0/12、扫描件题 0/14、记录准入题 0/10。
- 精确题中价格、KPI 口径、多字段合并等需要生成式回答的题目也失败。
- 产品对外表现为“模型服务不可用”，而不是“输入超限/证据过长”，排障成本高。

**建议**

1. 把“输入超限”从 `MODEL_UNAVAILABLE` 中拆出稳定错误码（如 `MODEL_INPUT_TOO_LARGE`），并在文案中说明。
2. 检索层按证据字节预算裁剪/分组，保证 payload 不超过闸门。
3. 若产品设计允许，提高 `chat_max_input_tokens` 并与 GO/预算 profile 同步；当前 1M context 只用于预留，实际 payload 只有 6KB。

### P0-2：并发问答触发受控执行器停机，索引进入 degraded 且不会自动恢复

**现象**

- 同一会话并发提交两个问题时，两次请求都返回 HTTP 200，而不是契约要求的 `409 QUESTION_IN_PROGRESS`。
- 并发触发了 `CONTROLLED_REFUSED`，`rag_meta.product_sync_status` 变为 `degraded`。
- 此后所有问答（包括原本可用的精确记录题）返回 `INDEX_NOT_READY`。
- 重启服务后仍为 degraded；只有再次发布一份资料触发同步，才恢复 `ready`。

**证据**

- `rag_meta`：`product_sync_error_code=CONTROLLED_REFUSED`、`product_sync_error=向量层暂不可用，记录型/精确层仍可用`
- 并发测试：`concurrent statuses 200 200`，随后 `INDEX_NOT_READY`
- 恢复测试：发布 `QA-恢复索引.xlsx` 后 `product_sync_status=ready`，E002 恢复回答

**影响**

- 一次并发点击/重试即可让整个知识库问答不可用，且无自愈入口。
- 与“每会话同时仅处理一个问题”和“失败可重试”的契约不符。

**建议**

1. 会话级在途锁必须在进入检索/模型前生效，第二个请求直接 409。
2. `CONTROLLED_REFUSED` 应被视为“本次拒绝”，不应永久停机；至少区分“并发拒绝”和“失败停机”。
3. `ensure_ready` 遇到 degraded 应做一次有界重同步，而不是永久返回 `INDEX_NOT_READY`。
4. 运营页/健康检查应暴露 `product_sync_status`，让管理员能看到 degraded。

### P1-1：未来生效资料未按业务基准日过滤，V02 污染当前答案

**现象**

- V02（标注 2026-11-20 生效）发布后，当前业务基准日 2026-10-28 的精确题出现 5 个 `conflict`、2 个 stale 冲突、1 个 rrem 冲突。
- 例：E001 返回“E区5号货架第二层（V02）”与“店内外侧（E11）”冲突，而不是 E11 的当前值。
- `rag_chunks.effective_from` 对 V02 为 `NULL`。

**根因**

- V02 使用列名“更新日期”；产品字段角色把“更新日期”映射为通用 `date`，而 `effective_dates()` 只识别 `effective_from`（生效日期/开始日期/生效时间）。
- 因此 V02 的行没有生效日期，业务基准日过滤不起作用。

**影响**

- 精确题 5 个直接冲突；E021 甚至从 V02 取到了未来值。
- 用户会看到“资料冲突”，但实际是“未来版本未生效”。

**建议**

- 明确“更新日期/业务更新日期”是否应作为生效日期；若应，加入 `effective_from` 同义词。
- 或在导入/发布时要求显式提供生效日期，避免依赖列名猜测。

### P1-2：OCR 版式判断把海报/价签误判为表格，导致上传失败

**现象**

- C05（夏季主推海报设计稿.png）、C06（门店价格标签实拍样张.jpg）任务失败：
  - `OCR_TABLE_UNRELIABLE`
  - 文案：“表格少于两行，缺少可确认的表头与数据”
- 这两份是海报/价签，不是表格；启发式 `looks_like_rule_table` 将其判为 `table`。
- 14 道 OCR 题因此 0 通过（另有 LLM 闸门因素）。

**建议**

- 表格模式失败时回退一次 text 模式，而不是直接判失败。
- 或在 OCR 结果不足两行时自动降级为 text，并记录降级原因。
- 对海报/价签类图片提供显式模式或更稳的版式分类。

### P1-3：单请求 60 秒总时限未被遵守

**现象**

- E064（“同一门店端架与堆头的 SKU 数量上限是多少？”）：
  - `started_at=13:07:04`
  - `deadline_at=13:08:04`（60 秒）
  - `finished_at=13:08:43`（实际 99 秒）
- 客户端 90 秒超时，未拿到结果；服务端最终写入 `MODEL_TIMEOUT`。

**影响**

- 前端 75 秒主动超时，用户看到的是网络错误；服务端仍在跑，可能重复计费/重复请求。

**建议**

- 在检索、模型、结算各阶段统一使用剩余 deadline，而不是各自的 30/60 秒。
- 超时后尽快落库并返回，不要让请求在 deadline 之后继续执行。

### P1-4：门店联系人/电话类问题被整体判为“受限个人信息”

**现象**

- E041–E048（8 道 exact）均返回：
  - “该请求要把物品记录与店家联系人、电话或地址等个人联系信息合并提供，属于受限个人信息范围，不能据此作答。”
- 答案键期望返回渠道类型、店长、联系电话。

**判断**

- 这可能是产品有意的隐私策略，但与答案键/业务预期冲突。
- 需要产品明确：单店联系人是否属于可回答范围；若可，应支持按权限/按字段回答；若不可，答案键应调整。

### P2-1：澄清误判

- E018“临港店的包柱海报（标识：QF18）放在哪里？”被判定“问题中包含多个物品”，候选为“包柱海报/宣传海报”。
- 共 7 题返回 clarification，其中多题期望 answer。
- 说明物品词表/实体识别对“包柱海报”这类复合词拆分过度。

### P2-2：版本移除 QF21 后，答案从未来版本取值

- V07 作为 E11 的新版本发布后移除了 QF21。
- E021 期望 E11 当前值“赠品暂存架”，实际返回 V02 的“F区4号货架第一层”。
- 与 P1-1 同源：V02 未按生效日期过滤。

### P2-3：重试接口语义与预期不同

- 对已成功但资料已删除的任务重试：返回 `410`，不是 `409`。
- 对不可重试的失败任务（如 OCR_TABLE_UNRELIABLE）重试：返回 `409`，不是 `202`。
- 行为本身有合理性，但错误码/文案需要与契约对齐，前端应能区分“可重试/不可重试/资料已删除”。

### P2-4：上传层与解析层的拒绝阶段不一致

- B02（51 页）→ 上传层 `422 PDF_PAGE_LIMIT`
- B05（损坏 docx）→ 上传层 `422 FILE_CORRUPT`
- B06（损坏 xlsx）→ 上传层 `415 INVALID_FILE_TYPE`
- B07（加密 PDF）→ 上传层 `415 FILE_ENCRYPTED`
- manifest 的 `expected_rejection` 标注为 `parse`。
- 实际更早拒绝是更安全的，但测试口径/文档需要同步。

### P2-5：边界 OCR 失败信息不够精确

- B08（无文字图片）→ `OCR_UNAVAILABLE`，不是“未识别到文字”的空结果。
- B09（模糊图片）→ `OCR_BUDGET_REFUSED`，因为 OCR 硬上限 13 次已用完。
- 两者都在 manifest 中标注为 `expected_rejection: ocr`，可接受；但 UI 文案应区分“无文字”“额度不足”“识别失败”。

- 上传 → 解析成功 → 发布 V1。

## 6. 测试结论

1. **资料管理链路整体可用**：上传、解析、OCR（多数）、发布、版本、取消、删除、预览、原件、同名/重复校验均按预期工作。
2. **问答链路存在阻断级问题**：LLM 请求在本地预发送阶段被 6144 字节闸门拒绝，导致 84/155 题服务异常；账本可证明 0 次 chat 调用。
3. **并发会永久性降级索引**：一次并发请求即可让 `product_sync_status=degraded`，后续问答全部 `INDEX_NOT_READY`，重启不自愈。
4. **未来生效资料未过滤**：V02 的“更新日期”未被识别为生效日期，污染 8 道题的答案/冲突判断。
5. **OCR 版式误判**：海报/价签被判为表格，C05/C06 上传失败。
6. **前端主流程可用**：双角色、问答、来源、资料、运营、移动端、上传均通过；唯一 UI 断言失败为测试选择器问题。

## 7. 建议修复顺序

1. P0-1：拆分/修复 chat 输入闸门，保证语义题能真正调用模型。
2. P0-2：会话级并发锁 + `CONTROLLED_REFUSED` 不永久停机 + degraded 自动重同步。
3. P1-1：明确并实现“更新日期/生效日期”语义，修复业务基准日过滤。
4. P1-2：OCR 表格失败回退 text，修复海报/价签误判。
5. P1-3：统一 60 秒总 deadline。
6. P1-4：产品确认门店联系人隐私策略，调整实现或答案键。
7. P2：澄清词表、重试语义、上传/解析拒绝阶段与文档口径对齐。
