## 6 拟提 `HARD_MAX_REQUESTS`（实算依据）

现 `HARD_MAX_REQUESTS = 1000`（`p2_contracts.py:87`），`MAX_GO_REQUESTS = 1000`（`live_authorization.py:94`），
两者被 `tests/evaluation/test_p2_authorization.py:481` 钉成同一个值。逐项实算：

| 项 | 请求 | 依据 |
|---|---|---|
| 已用 | 547 | 账本 reservation 计数 |
| T207 公开矩阵 | 255 | 本文件 §3（计划声明 254，累计实际 255） |
| T207 H2 回合 | 144 | 36 回合 × 4 |
| T207 H2 灌库 | ≤ 68 | 声明包的批数上界（§5 的 W+P+L+X+V 例） |
| T208 judge（3 元额度） | ≤ 160 | `floor(3.00 / 0.018688)`（judge 走 chat 上界，自动重试 0） |
| T900 independent（2 元额度） | ≤ 107 | `floor(2.00 / 0.018688)` |
| 小计 | **1,281** | |
| +20% 余量（同 T206 口径） | **1,537** | |
| **建议 `HARD_MAX_REQUESTS`** | **1,600** | 仍在主人预授权「≤2000」内，且整百便于审计 |

配套值（逐项都在 1600 以内，且各自留出重授权余量）：

| 计划 | `plan.max_requests` | 理由 |
|---|---|---|
| `PM/T207-plan-v0_1.json`（**现在**绑定） | **1000** | 当前代码上限；`547+254=801 ≤ 1000`，**只有 R1 能被授权** |
| 同一计划提顶后重发（只改 `max_requests`） | **1200** | 四次授权：801 / 777+254=1031 / 796+254=1050 / 802+254=1056 均 ≤1200 |
| H2 计划（封存进程生成） | **1100** | 进 H2 时已用≈802，`802+144+68=1014 ≤ 1100` |
| T208 judge 计划 | **1200** | 已用≈1014，`+160=1174` |
| T900 independent 计划 | **1400** | 已用≈1174，`+107=1281` |

**为什么现在交付的 GO 仍写 1000**：候选 GO 必须能与**当前**计划逐值绑定（`go_plan_sha256`），而当前代码拒绝
`plan.max_requests > 1000`（负例 `hard_cap_over_1000` → `request_cap_over_hard_limit`）。提顶后只需：
改 `build-plan.py` 的 `MAX_REQUESTS=1200` → 重跑 → 新 `plan_sha256` → 经理按新 sha 签发 → GO `max_requests=1200`。

**到值即停**：① `HARD_MAX_REQUESTS=1600` 是全历史累计硬顶，账本 reservation 计数到 1600 时
`request_limit` 在任何发送前拒绝；② 每张计划自己的 `max_requests` 是更早的闸（如公开计划 1200）；
③ 任一授权被 `request_budget_insufficient` 拒 = 停并报告，不静默加计划。
