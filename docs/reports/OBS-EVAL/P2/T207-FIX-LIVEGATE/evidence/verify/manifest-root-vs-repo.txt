## 2. 代码事实（决定哪条路径"能读"）
- `_load_holdout`（backend/src/mktkb/evaluation/p2_dataset.py:533-552）：先 `_require_env(MKTKB_P2_HOLDOUT_ROOT)`、
  再 `manifest_resolved.is_relative_to(root_resolved)`（:541-546），不满足即 `holdout_manifest_outside_root`，
  且该 raise 在 `_read_key` / 读取任何密文（:549-552）之前 —— 即"repo 副本不得用于 holdout 加载"。
- `p2-h2-plan` 走 `load_holdout_manifest`（backend/src/mktkb/evaluation/p2_holdout_plan.py:165-181）＝普通文件读 + 严格解析，
  不做 root 约束，因此生成计划用**仓库副本**合法（runbook :199-205 保持仓库路径是对的）。
- `p2-run --visibility holdout` 与两步 `p2-score` 均经 `load_p2_dataset(..., visibility="holdout")`
  （cli.py:597 / p2_score_run.py:462-466）→ 必须用 root 内那份。

## 3. 只读探针（不读 key、不读密文、不出网）
```
HOLDOUT_ROOT_ENV = MKTKB_P2_HOLDOUT_ROOT | HOLDOUT_KEY_FILE_ENV = MKTKB_P2_HOLDOUT_KEY_FILE
root_manifest inside root ?  True
repo_manifest inside root ?  False
repo copy rejected: holdout_manifest_outside_root | holdout_manifest_outside_root: holdout 的 manifest 必须位于封存 root 内
```

## 4. 结论
- runbook §8 三处 holdout 命令（p2-run + 两步 p2-score）已改为 `D:/mktkb-p2-holdout/v2/manifest.json`，该文件存在且
  sha256 与仓库副本一致（8874985e…），故 `manifest_sha256`、计划与产物身份不受影响；
- `p2-h2-plan` 仍用仓库副本，与代码事实一致；
- 探针证明：用仓库副本做 holdout 加载会被 `holdout_manifest_outside_root` 拒（修复前文档写法会直接阻断 H2 执行）。
