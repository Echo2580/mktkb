# T207 四案例受控诊断预案（未授权执行）

## 结论

现有 H2 v3 入口没有按题号或回合选择的参数。若主人未来决定通过真实产品重测四案，当前接口能实施的最小范围是 **完整 r0 + 完整 r1**：合计 **20 题、24 回合**，而非只运行四题六回合。两次各执行一次时，按现有计划结构合计最多 **115 笔计划内预留请求**。这是计划项上界，**不是一个独立的 115 次累计硬闸**；现有入口的累计计划/GO 上限固定为 1500，且重复执行仍受该累计上限约束。

本文件只是只读预案：尚无真实诊断授权；不签 GO、不生成私人计划、不执行入口。四个真实案例仍未闭环，真实诊断及独立 AI 验收的时机与范围由主人决定；诊断须以当时明确批准的额度和最新账本快照为准。保管角色处理私有材料；开发/经理不读取真实题面、答案、私人计划、key 或密文。

## 接口能力和最小范围

`tools/p2_h2_v3_controlled_execute.py` 的 CLI 只有：

| 子命令 | 现有参数 | 作用及限制 |
|---|---|---|
| `plan-private` | `--root`、`--key-file`、`--out-dir` 必填；`--created-utc`、`--max-requests` 可选 | 生成四场景计划与每场景 binding，写仓外新目录；当前代码要求 `--max-requests` **等于 1500**，传较小值被拒绝。只能由授权保管角色在主人批准后执行。 |
| `check-only` | `--binding`、`--run-index` 必填；`--plan-only`、`--plan-set`、`--out`、`--now` 可选 | 逐 run 核绑定、计划、GO、预算/账本和代码；`--plan-only` 跳过私有数据集重载，但仍会读取私有 binding/plan；完整模式重载受控私有契约。必须由有权角色操作。 |
| `run` | `--binding`、`--run-index`、`--out-dir`、`--evidence-root`、`--seal-root`、`--evidence-key-file` 必填；`--env-file`、`--now` 可选 | 一次只执行一个**完整场景**；输出、证据和封存目录须符合现有路径检查，首错停、无自动重试。没有 case/turn 选择参数，也没有 CLI 参数为两个 run 设置独立总费用或请求增量硬顶。 |

v3 `run_command` 从冻结契约 `bundle.contract.subset(scenario)` 取完整场景，校验场景 binding、完整题数/回合、计划及灌库；冻结 `ValidatedScenarioContract.validate_run` 也检查子集身份和 case 摘要。**不能通过删计划项、换子集或改标签实现四题诊断**；这种做法会触发绑定/契约拒绝。运行 r0 使用 `--run-index 0`，r1 使用 `--run-index 1`，不是使用题号参数。

两次实际执行都通过现有 live gate 使用**固定 GO 槽位**；`check-only` 对 r1 可模拟检查 pending GO，但**模拟成功不等于 r1 已在实际固定槽位获授权**。须由获授权角色按正式流程处理对应新 GO 的固定槽位及归档，不覆盖或复用旧证据；不能从 `--binding` 自动推断 pending GO 已切换。r0 与 r1 的新计划/GO 分别绑定各自 `plan_id/plan_sha256`，且应在每次发送前重新核查账本。

`check-only --plan-set` 只接受含 r0–r3 的四计划集合，汇总四 run 的计划请求；其 `quota.exceeds_gate` 是返回的汇总信息，代码的 `ok` 由 checks 决定，**不能把它当作单独 enforce 的“两 run 总额门”**。只批准 r0+r1 时，以单 run 实际预检和明确的操作步骤管理范围，不能把计划生成四份当成授权四次执行。

## 请求及费用

| 场景 | 用途 | 题/回合 | index_embedding 计划上界 | 逐回合最多 4 项 | 单次完整 run 计划上界 |
|---|---|---:|---:|---:|---:|
| r0 `base_b0` | 包含 C26 | 12 / 14 | 9 | 14 × 4 = 56 | **65** |
| r1 `base_b0_plus_v01` | 包含 C13、C22、C28 | 8 / 10 | 10 | 10 × 4 = 40 | **50** |
| 合计 | 两次各一次 | **20 / 24** | **19** | **96** | **115** |

依据：公开 `run/plan-regen/ingest-batch-census.json` 和 `run/diagnosis.md` 的逐源批数为 r0=9、r1=10；`p2_holdout_plan.py` 的 `TURN_OPERATIONS` 为每回合 query_embedding、rerank、query_expansion、answer 各最多 1 项，加一个 index_embedding 项；OCR 不在该模板中。目标四案合计六回合只是诊断关注面，不能按六回合计算实际请求上界。首错停、可选操作未发生、权限或预检拒绝可使请求低于上界；**入口可在发送前拒绝，因此无条件实际请求下界为 0**。即使 run 完成，具体 provider 请求数和费用也取决于真实分支与用量，不能声称必定花满 115 次或必为某个非零下界。

截至已核对快照：账本 **1273 / 1500**，余 **227**；项目 **22.8965946 / 40 元**，余 **17.1034054 元**；P2-LIVE **7.8256501 / 20 元**，余 **12.1743499 元**。账本 SHA `e007fee3456e5d13f737a82ed29af45eb4707e3576c444e3520d9ca941dc2899`，预算 SHA `79b21700b630be92148e2a8498ed47386dab08d6daa401601dc3d22a910b1a9e` 本次只读重核一致。若两次各一次均用满计划请求，算术累计 1388，低于 1500；但项目可能有并发或其他活动，不能用快照代替执行时检查。

按当前**代码冻结的计价画像及 token cap**做静态保守计算：embedding 每次 `4096×0.5/1000000 = 0.002048` 元；rerank 每次 `6000×0.8/1000000 = 0.0048` 元；chat 每次 `(6144×2+800×8)/1000000 = 0.018688` 元。每回合四项上界 `0.044224` 元，r0 计划上界 **0.637568** 元、r1 **0.462720** 元，合计 **1.100288** 元；单笔保守峰值 **0.018688** 元。这是按现代码画像计算的计划上界，不是已生成新计划、已通过预检、供应商报价保证或实际费用。实际准入以新计划重算及现行价格/上限校验为准，不联网核价。

历史参考：公开 `compose/compose-report.md` 记载先前四 run **126 次出站、0.2752902 元**；简单按每出站平均乘 115 得约 **0.2513 元**，仅为历史比例示意，**不是费用上限或可靠预测**；本次分支、模型用量、拦截及重试/重复调用情况可不同。计划模板自带成功估价约 r0 0.1329 + r1 0.0960 = **0.2289 元**，也是估价而非费用保证。

项目 40、阶段 20 和既有单请求 0.5 元边界不得改变；机器预留按计划保守值、授权单次上限和实际账本逐笔拒绝超限。计划默认成本中心 `answer_retrieval=8.5`、`ocr=6.5`、`judge=3`、`independent=2`，其合计为阶段 20。**当前 answer_retrieval 分中心已用额未在本只读预案中核实**；即使总项目和阶段余量看似足够，也不能保证两次 `worst_case_cny` 都通过中心预检。r0 后需用新账本重新核实 r1 计划 worst case、中心余量和 GO；预检不通过则停止，不调大额度或改预算。

## 新计划与新 GO 的可审阅条件

主人若决定进行，须明确授权：① 仅 r0、r1 完整场景各最多一次；② 可产生最多各 65 / 50 次计划内请求，合计计划量 115（但实际累计硬闸是 1500）；③ 项目/阶段/单笔预算边界维持 40/20/0.5 元；④ 只允许 index_embedding、query_embedding、rerank、query_expansion、answer，不含 OCR、judge 或 independent；⑤ 任何异常首错停止、不得自动重试；⑥ 证据仅由保管角色处理并输出安全固定码。若主人要求**机器强制累计新增不超过 115 次或新增花费不超过指定较低数额**，现有 v3 CLI/GO 与固定 1500 计划约束不足以表达该独立子预算，不能声称现有两 run 操作规程提供了该硬保证；需另行设计并经批准，当前不另造 harness、不改冻结件。

获准后，由保管角色用现有 `plan-private` 从仓外持有的已授权数据生成**新的完整四场景计划集**；计划绑定当前未提交工作树代码摘要、配置、数据/场景、run/date、计划哈希和 index 批次。源码已发生变化，旧计划可能因 `code_changed_since_plan` 拒绝，不能直接把旧计划或旧 GO 视为新授权。只对 r0/r1 准备新授权，其他场景生成计划不等于执行授权。

新 GO 必须符合 `p2_authorization.py` 固定 schema：顶层 `document`、`schema_version`、`stage`、`authorization`、`issued_by`、`nonce`、`issued_utc`、`expires_utc`、`budget_ledger_path`、`budget_ledger_sha256`、`budget_total_limit_cny`、`scope`；`scope` 只用现有 `plan_id`、`plan_sha256`、`operations`、`cost_centers_cny`、`stage_limits_cny`、`max_requests`、`max_request_cny`。不得发明 `max_new_requests`、自定义本轮花费顶等未支持字段。GO 必须绑定当前共享账本的有效摘要或校验允许的历史前缀，r0 后 r1 应重读并核验；有效期、固定槽位、计划哈希和全部费用中心均需匹配。

建议执行顺序（仅授权后，由保管角色按现有接口操作，以下为参数结构而非待执行命令）：

1. `plan-private --root <仓外受控根> --key-file <保管侧key路径> --out-dir <仓外新目录> --created-utc <有效时间> --max-requests 1500`；不向开发者公开私有路径内容。
2. 为 r0 的新计划准备新 GO；`check-only --binding <r0绑定> --run-index 0` 做完整受控重载和逐项核验。预检需比较最新累计预留数、项目/阶段及 `answer_retrieval` 中心余量、代码与计划摘要、费用画像、GO 期限及固定槽位。
3. 仅当以上均通过且授权仍有效，`run --binding <r0绑定> --run-index 0 --out-dir <新目录> --evidence-root <新目录> --seal-root <新目录> --evidence-key-file <保管侧key路径>`；`--env-file` 按既有受控流程处理，不打印内容。完成或首错停止后对账、封存、核查是否残留 reservation。
4. 复核最新费用、请求、绑定和预算；将 r1 新 GO 按正式固定槽位流程处理后，先 `check-only --binding <r1绑定> --run-index 1`，再按同形 `run ... --run-index 1`。若任何条件不成立，不执行 r1。
5. 保管角色按预先约定对四案分别输出安全固定码与来源绑定；区分产品结果、matcher v2、保留旧判定及 unknown，不能把新结果自动写成 T207 总验收。

只跑两个场景不能产生冻结 composer 要求的完整四场景总卡；而历史报告还记录 v3 9/10/13/15 计划与冻结 composer 8/9/11/13 校验存在 `scenario_plan_mismatch`。本轮合成 binding 保留验证不等于真实 v3 官方组合卡已解决。此次若获准，仅作为诊断，不用它推导 30 题总通过率或发布结论。
