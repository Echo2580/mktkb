## A. 缺陷（可复现，附最小修复范围）

### D-1（低）增量补丁文本不可直接应用

- **现象**：`round-increment.diff` 全文件为 CRLF 行尾；而目标 `tools/p2_h2_controlled_execute.py` 在工作树中是 LF。以 `baseline/` 副本重建时，`git apply` 在前 5 个文件通过、在该文件报 `patch failed: tools/p2_h2_controlled_execute.py:1878`；`git apply --reject` 的搜索上下文显示行尾差异标记（`?`）。
- **复现**：
  1. 建临时 git 仓库，按 `baseline/` 结构放入 6 个原始文件；
  2. `git apply round-increment.diff` → 退出码 1，报上述行；
  3. 将补丁与目标按 `\r\n → \n` 归一后，用 `difflib.unified_diff` 重算 6 个文件 → 与交付补丁 6/6 段逐行一致。
- **影响**：仅影响“用补丁复算”的可用性；不改变内容正确性。已用归一化方式独立确认增量真实。
- **最小修复范围**：交付目录内重新生成一份行尾归一（LF）的补丁，或补充归一化重建脚本 + 说明；不改产品源码。

### D-2（低）编号标题前缀只对部分扩展名解后缀

- **现象**：`query.py::_document_core` 只剥 `xls/xlsx/doc/docx/pdf` 后缀。对 `D01_设备巡检表.csv` 这类标题，核心串会保留 `.csv`，`_match_document` 的 `core in question` 条件与“资料名线索”回退都可能匹配不上。
- **复现**：`_document_core("D01_设备巡检表.csv")` 返回含后缀的核心串；`_match_document("设备巡检表在哪里")` 得不到该文档。
- **影响**：当前语料为 xlsx/docx/pdf 时无影响；若未来接入其他扩展名会静默失配。
- **最小修复范围**：要么把后缀剥离改为“已知扩展名集合可配置”，要么在文档/测试里显式声明仅支持三类扩展名并加一条断言测试。不改匹配算法主体。

### D-3（中，行为风险，未在真实语料验证）换题判定依赖宽词表，可能过度澄清

- **现象**：`intent.py` 用 `SWITCH_WORDS = ("换成","改为","另外","其他","不说","重新问","换个","再问一个","换一个话题")` 且要求上一轮未命名实体，才判“明确换题”。若上一轮出现“另外/其他”但并非真正换题（如“另外还有哪些通知？”），随后一个裸物品追问会被要求补门店。
- **方向**：保守（多一次澄清，不会答错门店/答错实体），但会降低可用性。
- **已做反例**：我构造“无换题词的普通裸追问” → 正常继承门店并作答（P12 通过）。
- **复现**：`parse_question("横幅呢？", context_questions=("另外还有哪些通知？",), context_entities={"store":"北园店"})` → 返回 clarification。
- **最小修复范围**：如需收紧，改为“上一轮自身产出了澄清或未解析实体”作为换题证据，而不是仅靠词表；或在词表上去掉歧义最大的“另外/其他”，并补一条“含另外但非换题”的反例测试。属产品行为取舍，须由主人/经理确认后再改。

### D-4（低）开工基线 diff 未覆盖 2 条文档路径

- **现象**：`baseline-tracked.diff` 仅 23 条代码/测试路径，`tracked modified` 为 25；缺 `.claude/handoffs/_index.md` 与 `docs/reports/OBS-EVAL/P2/T207-QUALITY-REPAIR/manager.md`。
- **影响**：不影响代码增量核验；但“开工基线完整记录”口径不严。
- **最小修复范围**：交付说明里注明基线 diff 仅覆盖代码/测试；或补这两条文档 diff。

### D-5（中，证据/流程）GO 与 PM 元数据的冻结基线缺口

- **现象 1**：4 份 GO（`P2-LIVE-GO.json`、`v3-r1/r2/r3.pending.json`）与 fix-2 快照 SHA 不同，本轮开工无这 4 条哈希。我实测 mtime 为 2026-11-15 16:43–16:47，早于本轮最早交付回执（`baseline-protection.json` 18:21:30），并与同目录 `v3-max1500-*.archived.json` 的 16:43–16:48 一致；但**无法证明本轮前后逐字节未变**。
- **现象 2**：两项公开 PM 元数据与 32 件冻结清单记录不符：`manager-acceptance.json` `bd44601c… → 502e41e1…`、`review-aggregate.json` `eeb72bc3… → d8c7abeb…`；两文件 mtime `2026-11-15T04:43:01+08:00`，**晚于冻结时刻 04:32:40 约 10 分钟**。
- **影响**：不能宣称当前 32/32；GO 槽位历史不可完全归因。
- **处置要求**：不得回填旧 hash、不得静默重签。由主人/经理决定：记录为已知偏差，或走正式重冻结流程（重冻结须同时留有旧值与原因）。
