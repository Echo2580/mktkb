# 市场部 AI 知识库 · 知识运营数据中台实施方案

2026-11-21 · 讨论稿 · 以 `codex/p2-e2e` 的 P2 收尾提交 `93486b6` 和当前相关源码为依据

## 一、首版解决什么问题

建议在现有管理端新增「知识运营」，以**异常问答诊断**作为首版主流程。管理员从总览发现未找到、冲突或服务异常，点开对应问答，查看结果、实际引用的资料版本和可用的执行阶段，再进入现有资料管理核查。运营总览提供入口，知识资产页解释哪些资料被实际采用。第二阶段再加人工复核、资料补充与回归验证。

这是面向现有知识库的运营模块。首版采用 **React + ECharts、FastAPI 和现有 SQLite 数据源**，复用 P2 评测。假设服务仍在单部门、本地或内网试用，现阶段按时间、结果类型和已有资料字段筛选。部门筛选、员工使用趋势和市场业务分析分别依赖组织数据、独立账号和可靠业务台账。

**主关联键已具备。** 产品问答把 `ConversationRequest.id` 写入 Trace 的 `request_id`。按请求关联结果消息和一个或多个已记录的 Trace。重放和重试按接口契约区分，早期拒绝、Trace 关闭或写入失败可能缺少关联。`document_id` 够首版做文档标识，`version_id + unit_key` 定位一个版本内的来源单元。跨版本匹配另做规则。模型先显示可信的配置摘要或 `config_hash`，配置快照有独立需求时再新增。产品 Trace 的 `mode=local` 是当前中间件固定值，不能用它判定调用的是真实供应商还是本地模式。

## 三、页面与交互

| 页面 | 首版展示 | 可执行操作 |
| --- | --- | --- |
| 运营总览 | 今日/本周/本月问答、结果分布、当前生效资料、待审核版本、导入失败和数据更新时间 | 切日期，点「未找到」「冲突」「导入失败」等图表项进入带筛选的明细。 |
| 问答诊断 | 时间、结果类型、问题等列表字段。详情展示问题、最终答复、引用及版本、已记录的执行阶段和耗时。固定评测结果另设页签，标出数据集与批次。 | 从问题追到实际引用或资料管理。存在多个 Trace 时切换执行尝试。无 Trace 时仍可查看业务结果。 |
| 知识资产 | 当前版本、版本状态、文件类型、解析结果、最终引用次数和关联问答。 | 点文档查看版本、关联问答与导入失败原因。按文档和版本查看引用分布。 |

默认列表只展示完成诊断所需的摘要。详情按权限加载。图表以结果分布、趋势和可下钻的数字为主，用表格承接明细。业务主题、热门问题、处理工单和变更影响放到第二阶段。优先区分四种展示结果：「有效零值」「尚无数据或采集关闭」「尚未评测」「评测失败」。独立展示「部分覆盖」，例如 80 条问答中 52 条有 Trace。

## 四、采集和指标口径

首版后端按业务库查请求、引用、文档和导入任务，按 Trace 仓储查执行记录，按现有评测接口与制品查评测摘要。跨库在服务层按请求 ID 关联。统计按服务端统一时区聚合，时间范围采用左闭右开，先用有上限的查询和分页。遇到压测瓶颈，再按天增加可重建的汇总表。事件新增时用服务端可确认的业务记录做事实源，前端交互事件只记录使用行为。

| 指标 | 建议口径 |
| --- | --- |
| 已完成问答量 | 按所选窗口内已提交结果的 `request_id` 去重，使用完成时间。幂等重放不加量。未提交结果的超时、拒绝或中断单列为请求状态。 |
| 有引用回答占比 | 有合法持久引用的 `answer` 请求数 ÷ `answer` 请求数。无分母时显示无样本。另展示未找到、冲突、需追问、服务异常、知识已变更的结果分布。引用覆盖不能代表业务正确率。 |
| 文档最终引用次数 | 在窗口内按 `result_message_id + document_id` 去重。版本页按 `result_message_id + version_id` 去重。一条回答引用同一文件多行只计一次。冲突提示中的来源单独标注。 |
| 文档与导入 | 文档数按未删除文档计，有效文档按当前生效版本计，待审核版本按 `review_required` 计。导入失败按任务结果或错误码展示，任务重试次数单列。 |
| 延迟与资源 | 业务问答量与 Trace 尝试数分别计。P50/P95 基于有耗时的实际执行样本，并显示样本数。Token 与费用显示已记录金额及覆盖率。账本保守结算、估算和供应商实账各自说明来源。 |
| 质量与活跃 | 固定集展示实际执行范围、样本数、硬门禁与分数。Ragas 单独显示指标和评测状态。活跃仅按在窗口内有问答记录的账号去重，共享账号无法代表员工人数。 |

需要检索量时，第二阶段对新请求采集受限的候选元数据。每个采样结果记录 `request_id`、执行尝试、阶段、来源版本和单元、排名或适用时的分数，封顶并区分是否截断。上线日期和覆盖率随指标展示。先用最终引用及资料版本构建可查的关系链，再扩展候选。P2 受控评测的较丰富证据继续按原授权读取。

## 五、数据、迁移与接口

**首版优先只读。** 现有业务库、检索库、Trace 库和评测制品各自保留。新增运营查询服务和页面，查询有需要时增加 Alembic 索引迁移。上线前用旧版本数据库副本核对查询、升级和耗时。关闭运营入口时，P2 问答、资料和引用按原路径运行。需要撤销迁移时使用经过验证的备份或回退方案，保留已生成的运营记录。

**第二阶段增量建表。** 反馈表关联员工本人的结果消息，同一用户与消息的反馈可更新。问题工单表关联请求、引用版本、分类、状态和责任人，并保留处理记录。评测任务和结果保存运行 ID、样本身份、知识库 revision、评测配置与结果状态。候选元数据按需放在受限存储，便于单独设置保留时间。新表通过 Alembic 逐步引入，历史统计只从已有事实重算，保留缺项和最早可用日期。

| 阶段 | 拟增加的接口 | 用途 |
| --- | --- | --- |
| 一 | `GET /api/v1/operations/overview` | 返回指标、趋势、窗口、口径版本、覆盖率和异常明细筛选条件。 |
| 一 | `GET /api/v1/operations/requests` 与 `GET /api/v1/operations/requests/{request_id}` | 查询请求和诊断详情。支持时间、结果类型和游标。复用现有 Trace、评测运行摘要与来源服务中的可共享能力。 |
| 一 | `GET /api/v1/operations/documents` 与 `GET /api/v1/operations/documents/{document_id}` | 查询资产、引用、版本和处理状态，支持文件类型、状态和分页。 |
| 二 | `PUT /api/v1/messages/{message_id}/feedback` | 员工提交或更新本人消息反馈，服务端校验归属及请求防伪。 |
| 二 | `/api/v1/operations/issues` 与 `/api/v1/operations/evaluations` | 管理员处理工单、创建受控评测任务并查询状态。写入接口要求权限和幂等控制。 |

## 六、异步任务与治理闭环

第二阶段从「未找到」、员工反馈和冲突结果筛出候选，用已有枚举、实体和引用信息进行初步分类。相似问题可先按规范化主题与实体合并，积累样本后再评估语义聚类。管理员区分资料缺失、检索遗漏、解析失败、版本过滤、模型误用和证据不足。只有人工确认的资料缺失才进入补录任务，其余回到对应的处理步骤。

资料沿用现有审核发布。发布后按版本及既有引用定位**曾经依赖该版本**的历史问答，并对匹配到的场景执行定向回归。历史答案保留原 revision。Excel 优先用明确的记录业务键和字段比对，Word/PDF 先用可靠标题或条款号找候选，匹配不确定时交人工复核。已引用答案的影响范围可以直接查到，曾被召回但未引用或旧版未命中的问题依赖补充采集或额外回归样本。

评测在独立任务队列异步执行，可复用导入任务的租约、心跳和过期续跑设计。任务记录待执行、执行中、完成、失败或受限。按样本、目标 revision、评测策略与配置防重复。默认执行已有离线规则和固定集，真实服务评测继续沿用授权、预算和调用上限。采集或评测故障只影响运营数据，问答和发布的原有流程继续运行。

所有运营查询由服务端校验管理员权限。问题和答案正文按需从业务记录取，不复制到 Trace 或图表数据。旧版或撤销来源只展示当前权限允许的信息。生产诊断候选元数据采用字段白名单，设置短期保留和访问审计。外部平台接入前确认允许发送的字段与用途。保留期限、管理员可查看的问答正文范围、员工是否收到处理结果，作为上线前的业务决定。

## 八、开发顺序与验收

| 阶段 | 交付及依赖 | 可验证的验收标准 |
| --- | --- | --- |
| 0 · 数据验证 | 核对本地试用配置及记录覆盖，确认指标字典。依赖有代表性的隔离数据。 | 跑一组受控问答，在业务记录、引用及 Trace 之间完成关联核对。验证一次重放、一次无 Trace 和一次版本替换，说明可关联与缺失的范围。 |
| 1 · 可视化和诊断 | 开发总览、问答诊断、知识资产，接现有评测摘录。依赖阶段 0 的数据口径。 | 明细按时间与状态过滤后可复算图表数字。多引用及重放用例不重复计数。Trace 关闭时业务指标仍可查。非管理员无法查询运营详情。旧版/撤销引用遵守原权限。以隔离库做 P2 回归。 |
| 2 · 反馈和资料治理 | 新增反馈、工单、变更影响、后台回归。依赖明确的正文访问范围、样本保留规则及发布动作。 | 人工复核后能从问题走到资料补录、审核、发布和回归。重复提交及任务重试不产生重复业务结果。能识别一次条款更新和已引用旧版本的问答。报告区分未评测、评测失败和评测完成。 |
| 3 · 按业务扩展 | 统计聚合、跨工具入口、市场业务分析或更广的资产关系，按实际需求选择。 | 用实测数据确定投入。业务报表至少能与来源台账逐项对账，扩容须有同口径压测结果。 |

本稿依据源码与官方文档核对能力。试用流量、Trace 覆盖率、查询性能和第三方组件集成效果尚待实测。首要讨论点是**哪类异常最值得管理员每天处理**。建议先拿「未找到」和「冲突」跑通真实运营流程，再决定首版是否同时开放员工主动反馈。
